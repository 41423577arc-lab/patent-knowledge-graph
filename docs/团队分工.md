# 团队分工方案（5 人 / 两天）

> 配套文档：[项目规划.md](项目规划.md)
> 原则：**前端一个人包干，后端两个人各管一摊；不做需要反复对齐的横向拆分。**

## 一、分工原则

本项目采用"**垂直切片 + 单一所有权 + 冻结契约**"：

- **前端集中在 P3 一个人手里**，三个页面由同一人写，样式天然统一，不需要互相看页面。
- **后端由 P1、P2 两个人分**：P1 管"数据与图谱"，P2 管"问答服务"。
- **P3 顺带做一点后端**：只做页面需要的简单取数和聚合，不做 PageRank、中心性、大模型这些重活。

三条硬规则：

1. **一个文件只有一个主人。** 别人只能读，不能改。
2. **一个人负责一条完整的链路**，不跨人拼装同一个功能。
3. **需要对接的地方，只允许通过"冻结的接口契约"对接**，不允许靠口头沟通对齐。契约在 T0 一次性定死。

这样做的结果：

- 三页视觉统一**不再需要跨人协调**，因为只有一个前端。
- P1 和 P2 **互不改代码**，各自的后端模块独立。
- P2 给 P3 一个 `answer()` 接口，P3 在 T0 拿到"假数据桩"就能先搭页面，不用等问答做完。
- 唯一的"先后关系"是 T0 的框架交付，属于"提供方给框架、使用方在框架里做"，不是"做完一个功能才能开始下一个"。

|---|---|---|---|---|

| P3 | 前端与页面取数 | 核心技术 | `app.py`、`pages/`、`ui/`、`analysis/`、`docs/ui_spec.md` | 三个页面、图表交互、页面级查询、统一视觉 |
| P4 | 文档与汇报 | 非技术 | `docs/说明文档.md`、`docs/ppt/`、`docs/答辩稿.md` | 说明文档、PPT、答辩稿 |

- P1 不写页面、不写问答。

- P4、P5 不改任何业务代码，只读 `core/` 和产物文件。

## 四、接口契约（唯一需要对接的地方）

所有契约在 **T0（今晚）冻结**。冻结后任何改动必须走第五节的变更流程。

### 契约 A：Neo4j Schema（P1 提供，P2/P3 使用）

节点：

```text
(:Patent {patent_id, title, abstract, apply_date, apply_year, pub_date,
          patent_type, country, legal_status, is_in_sample})

(:Applicant {name, raw_names, type, country})

(:IPC {code, name, level})

(:Technology {name, keywords, description})

(:Domain {name, description})
```

关系：

```text
(:Applicant)-[:APPLIES_FOR]->(:Patent)
(:Patent)-[:CITES]->(:Patent)
(:Patent)-[:HAS_IPC]->(:IPC)
(:Patent)-[:INVOLVES]->(:Technology)
(:Technology)-[:BELONGS_TO]->(:Domain)
(:Applicant)-[:CO_APPLIED_WITH {weight}]-(:Applicant)
```

唯一约束与索引由 P1 在 `docs/schema.md` 写明，P2/P3 按此写 Cypher。**P2/P3 不得假设存在未写进 `docs/schema.md` 的字段。**

### 契约 F：问答服务（P2 提供，P3 调用）

这是 **P2 → P3 唯一的一条接口**。P2 不关心页面怎么画，P3 不关心里面怎么查。

```python
# qa/service.py —— P2 维护，P3 只调用
def answer(question: str, mode: str = "auto") -> dict:
    """
    mode: "auto" | "rule" | "llm"
    返回：
    {
      "ok": bool,
      "intent": str,
      "slots": dict,
      "entities": {"resolved": dict, "candidates": list},
      "data": list[dict],                 # 表格数据
      "graph": {"nodes": [...], "edges": [...]},  # 路径图
      "conclusion": str,
      "cypher": str,
      "mode": "llm" | "rule",
      "error": str | None,
      "suggestions": list[str],
    }
    """
```

**T0 交付桩：** P2 在 T0 先给一个 `service.py`，内部用两三个示例问题返回**结构合法的假数据**。P3 拿到桩就能搭页面三的 UI，不必等真实问答完成；T2 再切到真实实现。契约结构不变，P3 的页面代码不用改。

### 契约 G：UI 规范（P3 内部，不跨人）

因为三个页面都由 P3 一个人写，视觉统一是**单点所有权的自然结果**，不再是一条需要别人遵守的跨人契约。但仍然需要一套内部规范，防止自己前后三页写漂：

- `ui/theme.py`：`COLORS`、`apply_theme()`、Plotly 模板。
- `ui/components.py`：`page_header()`、`section()`、`metric_row()`、`chart()`、`data_table()`、`empty_state()`、`error_state()`。
- `docs/ui_spec.md`：页面结构、配色、术语、数字口径。

统一口径：

| 项 | 规定 |
|---|---|
| 页面顺序与标题 | `01 产业技术全景`、`02 创新主体与合作网络`、`03 智能问答与关联路径` |
| 页面结构 | 页头 → 筛选栏 → 指标卡 → 图表 → 表格/明细 |
| 术语 | 统一用"创新主体""技术主题""技术领域""依赖暴露度"；"企业"只在明确是企业时用 |
| 计数口径 | 默认统计样本内专利；涉及样本外时必须在图注注明 |
| 数字格式 | Top-N 默认 10；百分比 1 位小数；大数千分位 |
| 状态 | 空结果用 `empty_state()`，错误用 `error_state()`，不自造提示 |
| 图表 | 只用 `chart()` 套模板；图例、网格、字体一致 |

> 如果之后临时换人接手前端，这套 `ui/` + `ui_spec.md` 就是交接材料。

## 五、契约变更流程

1. 提出方在群里说明：改哪个契约、为什么、影响谁。
2. 由契约的**提供方**更新本文档与 `docs/` 对应文件。
3. 使用方按新契约修改，**不允许口头约定、不允许私自改字段**。
4. 变更只允许在 T0—T2 之间；T2 之后冻结，新增需求写入"后续扩展"。

## 六、依赖方向

```text
P1 ──契约 A/B/C──> P2
 │
 └──契约 A/B/C──> P3

P2 ──契约 F──────> P3

P5 ──契约 D──────> P2

P1/P5 ──契约 E───> P4
```

- **P1 和 P2 是两条互不改代码的后端线**：P1 数据与图谱，P2 问答服务。
- **P3 是唯一的前端**：页面一、二只依赖 P1；页面三只依赖 P2 的 `answer()`。
- P2 → P3 是一条**单向、冻结**的服务契约，不是"两个人一起做页面"。
- P3 在 T0 拿到契约 F 的桩，即可独立开发，不等 P2 完成。

## 九、协作规则

1. **文件所有权**：只改自己目录下的文件；需要别人改，提需求，不代改。
2. **禁止共享可变模块**：允许少量重复代码，不允许两个人维护同一个文件。
3. **开发开关**：P2/P3 默认 `USE_SAMPLE=True` 开发；T2 起切 `False` 联调。
4. **不硬编码**：路径走 `load_table`/`load_result`，连接走 `run_query`，配置走 `core/config.py`。
5. **密钥**：API Key、数据库密码只放 `.env` 或 Streamlit secrets，不进代码、不进压缩包。
6. **前端单点所有权**：只有 P3 改 `app.py`、`pages/`、`ui/`、`analysis/`；其他人只读，不提"你把这行改一下"，而是提需求由 P3 改。
7. **每日同步只报状态**：做了什么、卡在哪、是否需要改契约；不做设计评审、不互相改代码。
8. **若启用 git**：每人一分支（`p1-data`、`p2-qa`、`p3-frontend`、`p4-docs`、`p5-eval`），只合并自己的目录；本仓库已启用 Git，个人分支向 develop 提 PR，联调后合入 main。
