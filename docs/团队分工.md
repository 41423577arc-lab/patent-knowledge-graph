# 团队分工方案（5 人 / 两天）

> 配套文档：[项目规划.md](项目规划.md)
> 原则：**做小、做透、不做需要反复对齐的横向拆分。**

## 一、分工原则

本项目采用"**垂直切片 + 单一所有权 + 冻结契约**"，而不是"一个模块拆给两个人、各做一个功能再对齐"。

三条硬规则：

1. **一个文件只有一个主人。** 别人只能读，不能改。
2. **一个人负责一条完整的链路**（数据 → 查询 → 图表/问答 → 页面），不跨人拼装同一个功能。
3. **需要对接的地方，只允许通过"冻结的接口契约"对接**，不允许靠口头沟通对齐。契约在 T0 一次性定死，之后各自按契约开发。

这样做的结果：

- P2 和 P3 **完全不接触**，各自做各自的页面。
- P2、P3 只在 T0 接收 P1 交付的框架（Schema + 样例数据 + 取数函数），之后**不等 P1 的全量数据**也能开发。
- 唯一的"先后关系"是 T0 的框架交付，属于"P1 给框架、P2/P3 在框架里做"，不是"P1 做完功能、P2 才能开始"。

## 四、接口契约（唯一需要对接的地方）

所有契约在 **T0（今晚）冻结**。冻结后任何改动必须走第五节的变更流程。

### 契约 A：Neo4j Schema（P1 提供，P2/P3 使用）

节点：

```text
(:Patent {patent_id, title, abstract, apply_date, apply_year, pub_date,
          patent_type, country, legal_status, is_in_sample})

(:Applicant {name, raw_names, type, country})

(:IPC {code, name, level})

(:Technology {name, keywords, description})

(:Domain {name, description})
```

关系：

```text
(:Applicant)-[:APPLIES_FOR]->(:Patent)
(:Patent)-[:CITES]->(:Patent)
(:Patent)-[:HAS_IPC]->(:IPC)
(:Patent)-[:INVOLVES]->(:Technology)
(:Technology)-[:BELONGS_TO]->(:Domain)
(:Applicant)-[:CO_APPLIED_WITH {weight}]-(:Applicant)
```

唯一约束与索引由 P1 在 `docs/schema.md` 写明，P2/P3 按此写 Cypher。**P2/P3 不得假设存在未写进 `docs/schema.md` 的字段。**

## 五、契约变更流程

1. 提出方在群里说明：改哪个契约、为什么、影响谁。
2. 由契约的**提供方**更新本文档与 `docs/` 对应文件。
3. 使用方按新契约修改，**不允许口头约定、不允许私自改字段**。
4. 变更只允许在 T0—T2 之间；T2 之后冻结，新增需求写入"后续扩展"。

## 九、协作规则

1. **文件所有权**：只改自己目录下的文件；需要别人改，提需求，不代改。
2. **禁止共享可变模块**：允许少量重复代码（如各自的图表函数），不允许两个人维护同一个文件。
3. **开发开关**：P2/P3 默认 `USE_SAMPLE=True` 开发；T2 起切 `False` 联调。
4. **不硬编码**：路径走 `load_table`，连接走 `run_query`，配置走 `core/config.py`。
5. **密钥**：API Key、数据库密码只放 `.env` 或 Streamlit secrets，不进代码、不进压缩包。
6. **每日同步只报状态**：做了什么、卡在哪、是否需要改契约；不做设计评审、不互相改代码。
7. **若启用 git**：每人一分支（`p1-data`、`p2-pages`、`p3-qa`、`p4-docs`、`p5-eval`），只合并自己的目录；当前不是 git 仓库，按文件夹隔离即可。
