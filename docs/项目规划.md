# 新能源汽车产业技术情报知识图谱平台
## ——基于专利图谱的可解释智能问答与创新主体分析

# 一、项目概述

## 1.1 项目名称

新能源汽车产业技术情报知识图谱平台（EV Intelligence）

## 1.2 项目背景

随着新能源汽车产业持续发展，动力电池、电驱动系统、智能控制、充电设施及能源管理等技术领域不断演进，产业技术创新呈现出技术方向多样化、创新主体多元化和技术关联日益复杂等特点。

专利文献记录了企业、高校及科研机构在技术研发过程中的创新成果，包含专利申请人、技术分类、技术功效、专利引用及法律状态等多维信息，是分析产业技术布局和创新活动的重要数据来源。

然而，传统专利数据通常以表格形式存储，数据之间缺乏直观的关联表达，难以直接回答企业技术布局、创新主体合作、技术主题演化及技术依赖关系等复杂问题。

因此，本项目以新能源汽车产业专利数据为基础，构建专利、创新主体、技术领域和技术主题之间的关联网络，并在图谱之上实现"可解释的智能问答"，使用户可以用自然语言提出业务问题，系统返回图谱查询结果、关联路径与结论说明。

## 1.3 项目定位

本项目定位为面向企业管理人员、技术研发人员、产业分析人员及创业者的新能源汽车产业技术情报分析平台。

平台以专利知识图谱为底层数据支撑，通过三个业务页面，为用户提供产业技术概况、创新主体与合作关系分析、以及基于图谱的智能问答与关联路径查询功能。

平台重点解决以下问题：

1. 产业整体技术发展情况如何？
2. 哪些企业和机构是重要的创新主体？
3. 不同创新主体之间存在怎样的技术合作关系？
4. 某企业主要布局了哪些技术主题，这些主题属于什么技术领域？
5. 某企业的专利主要引用了哪些外部主体，是否存在技术依赖？
6. 哪些技术主题表现出较快的增长趋势，值得进一步关注？

## 1.4 项目建设目标

本项目拟实现以下目标：

- 构建新能源汽车产业专利知识图谱，实现专利、申请人、技术分类及技术主题等实体的关联组织。
- 利用专利申请量、引用关系及网络中心性等指标识别关键创新主体。
- 基于共同申请关系构建企业合作网络，分析创新主体之间的合作情况。
- 结合 IPC 分类和专利文本信息识别技术领域与细分技术主题。
- 基于专利引用关系构建"技术依赖暴露度"指标，识别外部技术依赖与单点依赖风险。
- 在知识图谱之上实现可解释的智能问答：自然语言问题经意图识别与实体链接后，由预置图谱查询返回事实，再由大模型组织结论。
- 开发包含"产业技术全景""创新主体与合作网络""智能问答与关联路径"三个页面的可视化网站。

## 1.5 项目约束与范围取舍

本项目为课程小组作业，开发周期约两天，小组规模 3—5 人。依据"做小、做透、说实话"的原则，明确以下取舍：

| 事项 | 决定 | 理由 |
|---|---|---|
| 页面数量 | 三页：全景 / 主体与合作 / 智能问答 | 两天内保证每页可运行、可演示 |
| 原"技术识别与主题演化""技术前沿识别" | 不单独设页，主题趋势与前沿识别收进全景页与问答意图 | 避免四页并行导致每块都浅 |
| 微软式 GraphRAG（实体抽取+社区摘要） | 不做 | 两天无法完成，且与专利结构化数据不匹配 |
| 图谱增强问答（KG-RAG 风格） | 做，作为核心创新 | 与作业"智能问答"方向直接对应 |
| 技术替代路径推断 | 不做为主功能 | 仅凭引用+增长难以自证"替代"，答辩风险高 |
| 技术依赖 / 风险传导 | 做，作为问答的高阶多跳意图 | 落在现有引用字段上，业务价值明确 |
| 大模型生成 Cypher | 不做 | 避免幻觉、注入与慢查询，保证现场稳定 |
| 演示降级 | 必做 | API 或网络异常时切换规则模板答案 |

# 二、系统需求分析

## 2.1 用户需求分析

平台主要面向以下用户群体：

| 用户类型 | 主要需求 | 对应功能 |
|---|---|---|
| 企业管理人员 | 了解产业技术发展方向和竞争主体 | 产业技术全景、创新主体识别 |
| 技术研发人员 | 了解具体技术领域及技术主题的发展情况 | 主题趋势、智能问答 |
| 产业分析人员 | 分析企业技术布局、合作关系与技术依赖 | 创新主体与合作网络、依赖路径问答 |
| 创业者及业务拓展人员 | 发现具有增长趋势的技术方向 | 前沿识别问答 |

## 2.2 能力问题清单

系统需要回答的业务问题如下。表中标注"多跳"的问题涉及三个及以上实体/关系的关联查询。

| 编号 | 能力问题 | 类型 | 涉及实体或关系 |
|---|---|---|---|
| CQ01 | 当前产业中专利申请量较高的企业有哪些？ | 单跳聚合 | Applicant、Patent |
| CQ02 | 哪些企业在专利引用网络中具有较高影响力？ | 网络分析 | Applicant、Patent、CITES |
| CQ03 | 某企业主要布局了哪些技术领域？ | 多跳 | Applicant、Patent、IPC |
| CQ04 | 哪些企业之间存在共同申请专利的合作关系？ | 多跳 | Applicant、Patent |
| CQ05 | 某一技术主题近年来的专利申请数量如何变化？ | 时间聚合 | Patent、Technology |
| CQ06 | 哪些技术主题表现出较高的年度增长趋势？ | 聚合计算 | Technology、Patent |
| CQ07 | 某企业的专利涉及哪些技术主题，这些主题分别属于什么技术领域？ | **多跳** | Applicant、Patent、Technology、Domain |
| CQ08 | 与某企业存在共同申请关系的企业有哪些，这些企业又分别布局了哪些技术领域？ | **多跳** | Applicant、Patent、Technology、IPC |
| CQ09 | 某企业申请的专利引用了哪些其他企业的专利，这些被引用专利涉及哪些技术领域？ | **多跳** | Applicant、Patent、CITES、IPC |
| CQ10 | 某企业的技术引用在多大程度上依赖外部主体，是否存在单点依赖？ | **多跳** | Applicant、Patent、CITES、Technology |

其中 CQ07、CQ08、CQ09、CQ10 为多跳问题，满足作业"不少于 5 个能力问题、至少 2 个多跳问题"的要求。

## 2.3 功能需求分析

系统设置三个核心功能模块。

### 模块一：产业技术全景

主要功能：

- 新能源汽车产业专利总量、创新主体数量、技术主题数量统计。
- 专利年度申请趋势分析。
- 专利类型及公开国别分布。
- 主要技术领域（IPC）分布。
- 技术功效分布。
- 主要创新主体排名。
- 技术主题年度趋势概览。

主要解决的问题：

从宏观层面了解产业的专利创新规模、技术领域分布及整体发展趋势。

### 模块二：创新主体与合作网络

主要功能：

- 创新主体专利申请量排名。
- 企业被引证次数排名。
- 企业 PageRank、度中心性、中介中心性。
- 企业技术领域布局。
- 企业共同申请关系识别。
- 企业合作网络可视化。
- 企业详情及关联专利查询。

主要解决的问题：

识别产业中的重要创新主体，分析企业的技术布局、创新影响力以及企业之间的合作关系。

### 模块三：智能问答与关联路径

主要功能：

- 自然语言问题输入，返回图谱查询结果。
- 意图识别与实体链接（企业名、技术主题名、年份范围）。
- 多跳关联查询（企业—专利—主题—领域、企业—引用—企业等）。
- 查询结果的可解释展示：命中的意图、参数、Cypher、返回子图与原始数据。
- 大模型基于查询结果生成结论说明（不生成查询、不编造数字）。
- 技术依赖暴露度与单点依赖识别。
- 示例问题与候选问题引导。
- 大模型不可用时的规则模板降级。

主要解决的问题：

让不具备图谱查询能力的用户，用自然语言直接获得可追溯、可解释的产业技术情报结论。

## 2.4 非功能需求

- 可用性：页面结构清晰，问答失败时给出可用问题提示与候选实体。
- 稳定性：查询只读、带超时与 LIMIT；大模型异常时自动降级。
- 可解释性：核心指标与技术主题识别规则具有明确计算口径；问答结论可追溯到查询与数据。
- 可维护性：数据处理、图谱查询、问答编排与页面展示相互分离。
- 可扩展性：支持后续增加专利数据、扩展技术分类与新增问答意图。

# 三、数据来源与数据处理

## 3.1 数据来源

本项目数据来源于 Incopat 专利数据库，选取新能源汽车产业相关专利作为研究对象。数据通过学校/机构授权账号导出，仅用于课程学习与研究，不对外传播原始数据。

数据包含专利基本信息、申请人信息、技术分类信息、技术功效信息、专利引用信息、法律状态信息及专利价值评价信息等。

主要使用字段包括：

| 数据类别 | 主要字段 |
|---|---|
| 专利基本信息 | 公开公告号、标题、摘要、申请日、公开日、专利类型、公开国别 |
| 申请人信息 | 申请人、标准化申请人、第一申请人、申请人终属母公司、申请人类型 |
| 技术分类信息 | IPC主分类、IPC、CPC、技术功效一级、二级、三级分类 |
| 专利引用信息 | 引证专利、被引证专利、引证次数、被引证次数 |
| 法律状态信息 | 专利有效性、当前法律状态、法律事件 |
| 专利评价信息 | 合享价值度、技术稳定性、技术先进性、保护范围 |
| 其他信息 | 发明人、同族专利、用途等 |

如 Incopat 数据无法及时获取，备选公开数据源为 CNIPA 专利检索系统、Google Patents 等；届时需同步更新本节的来源说明与字段清单。

## 3.2 数据探查

在清洗前先完成数据探查，并形成探查记录：

- 记录总数、字段数、去重后记录数。
- 各关键字段的非空率：公开号、标题、申请日、申请人、IPC、摘要。
- 重复记录检查：按公开公告号统计重复条数。
- 异常值检查：申请日格式、IPC 格式、公开国别取值分布。
- 时间跨度与年度分布。
- 申请人名称的原始表达数量与标准化后数量对比。

## 3.3 数据预处理

### （1）数据清洗

- 删除完全重复记录。
- 统一专利公开号格式。
- 处理空值和异常值。
- 统一日期格式。
- 清理标题、摘要中的异常字符。
- 统一申请人名称格式。
- 处理 IPC 分类号中的多个分类项。

### （2）专利实体识别

以公开公告号作为专利唯一标识，建立专利实体。对于缺少公开公告号或存在异常标识的记录，单独处理，避免产生重复实体。

### （3）申请人实体归一化

以标准化申请人作为企业实体匹配的主要依据，保留原始申请人名称作为属性。

对同一专利存在多个申请人的情况进行拆分，建立专利与多个申请人之间的关联。建立"原始名称 → 标准名称"别名表，用于处理"比亚迪股份有限公司 / 比亚迪 / BYD"等表达差异。

### （4）专利引用关系处理

从引证专利和被引证专利字段中提取专利之间的引用关系，统一引用方向：

`专利A -[CITES]-> 专利B`

表示专利A引用了专利B。区分样本内部专利与样本外部引用专利：外部专利可作为被引用节点存在，但不计入样本专利总量，并尽量补充其申请人信息以支撑依赖分析。

### （5）技术分类处理

提取 IPC 主分类及完整 IPC 分类号，建立专利与技术分类之间的关联。对多个 IPC 分类号进行拆分，使一项专利可以关联多个技术领域。

### （6）文本处理

对专利标题、摘要、技术功效短语等文本进行清洗和标准化，为后续关键词提取与技术主题识别提供基础数据。

## 3.4 数据规模统计

图谱导入完成后，统计并记录以下规模指标（用于说明文档与答辩展示）：

| 统计项 | 数值 |
|---|---|
| 清洗后专利数 | 导入后统计 |
| 申请人（标准化）数 | 导入后统计 |
| IPC 分类数 | 导入后统计 |
| 技术主题数 | 导入后统计 |
| APPLIES_FOR 关系数 | 导入后统计 |
| CITES 关系数（样本内 / 含样本外） | 导入后统计 |
| HAS_IPC 关系数 | 导入后统计 |
| INVOLVES 关系数 | 导入后统计 |
| CO_APPLIED_WITH 关系数 | 导入后统计 |

# 四、知识图谱设计

## 4.1 Schema 设计

### （1）核心实体类型

| 实体类型 | 英文名称 | 唯一标识 | 主要属性 |
|---|---|---|---|
| 专利 | Patent | 公开公告号 | 公开号、标题、摘要、申请日、公开日、专利类型、法律状态、是否样本内 |
| 申请人 | Applicant | 标准化名称 | 标准化名称、原始名称、申请人类型、国家地区 |
| 技术分类 | IPC | IPC分类号 | IPC分类号、分类名称、分类层级 |
| 技术主题 | Technology | 主题名称 | 主题名称、关键词、主题描述 |
| 技术领域 | Domain | 领域名称 | 领域名称、领域描述 |

### （2）核心关系类型

| 关系类型 | 英文名称 | 起点 → 终点 | 含义 |
|---|---|---|---|
| 申请 | APPLIES_FOR | Applicant → Patent | 申请人申请专利 |
| 引用 | CITES | Patent → Patent | 引用方专利引用被引用专利 |
| 技术分类 | HAS_IPC | Patent → IPC | 专利具有某个 IPC 分类 |
| 涉及技术 | INVOLVES | Patent → Technology | 专利涉及某个技术主题 |
| 领域归属 | BELONGS_TO | Technology → Domain | 技术主题属于某个技术领域 |
| 共同申请 | CO_APPLIED_WITH | Applicant ↔ Applicant | 两个申请人曾共同申请专利，权重为共同申请数 |

### （3）关系结构示意

```text
(Applicant)-[:APPLIES_FOR]->(Patent)

(Patent)-[:CITES]->(Patent)

(Patent)-[:HAS_IPC]->(IPC)

(Patent)-[:INVOLVES]->(Technology)

(Technology)-[:BELONGS_TO]->(Domain)

(Applicant_A)-[:CO_APPLIED_WITH {weight}]-(Applicant_B)
```

企业之间的共同申请关系与专利引用关系分别处理，不将引用关系直接解释为企业合作关系。

## 4.2 实体与属性的取舍依据

作业要求说明"为什么把某个对象设计成实体而不是属性"。本项目的取舍依据如下：

| 对象 | 设计为 | 取舍理由 |
|---|---|---|
| 专利 | 实体 | 需要被多个申请人、IPC、主题共享，并作为引用关系的端点 |
| 申请人 | 实体 | 需要跨专利聚合、参与合作网络与中心性计算 |
| IPC 分类 | 实体 | 一项专利可对应多个 IPC，一个 IPC 也被多项专利共享；若作为属性将无法按分类聚合 |
| 技术主题 | 实体 | 需要跨专利聚合、按年度演化、与领域建立归属关系；若作为属性则无法做主题网络与趋势分析 |
| 技术领域 Domain | 实体 | 作为技术主题的上层归类，支撑"主题—领域"多跳查询 |
| 申请年份 | 专利属性 | 仅作为统计维度，不需要被其他实体共享，建实体会造成冗余 |
| 专利标题、摘要 | 专利属性 | 文本内容服务于展示与主题抽取，不参与关系连接 |
| 引证次数、被引证次数 | 专利属性（可预计算） | 用于排序展示，避免每次查询实时聚合 |
| 申请人原始名称 | 申请人属性 | 别名信息需保留以支撑实体链接与解释，但不作为唯一键 |
| 引用关系 | 关系 | 引用是专利之间的直接连接，建为关系才能支持多跳路径查询 |

## 4.3 关系方向的语义说明

- `APPLIES_FOR`：由申请主体指向被申请的专利，方向表示"谁申请了什么"。
- `CITES`：由引用方指向被引用方，`A -[CITES]-> B` 读作"A 引用了 B"，与专利文献中"引证"的方向一致。
- `HAS_IPC`：由专利指向分类号，表示"该专利属于该分类"。
- `INVOLVES`：由专利指向技术主题，表示"该专利涉及该主题"。
- `BELONGS_TO`：由技术主题指向技术领域，表示"该主题归属于该领域"。
- `CO_APPLIED_WITH`：语义上无向，存储时按字典序规范化方向并写入权重，查询时按无向匹配，避免重复边。

# 五、知识抽取与融合

## 5.1 专利实体抽取

从原始专利数据中提取专利公开号、标题、摘要、申请日期、公开日期、专利类型及法律状态等属性，形成 Patent 实体，并标记是否为样本内专利。

## 5.2 创新主体抽取

从申请人、标准化申请人等字段中提取企业及机构信息。通过标准化名称进行实体归一化，处理同一申请人存在不同名称表达的问题。

归一化流程：

1. 以标准化申请人字段为主键。
2. 建立原始名称到标准名称的别名表。
3. 对标准化后仍存在差异的名称，用编辑距离（rapidfuzz）辅助合并，并保留人工确认记录。

## 5.3 技术领域抽取

利用 IPC 分类号识别专利所属的技术领域。对 IPC 分类号进行拆分和层级映射，建立专利与技术领域之间的关联。技术领域划分以 IPC 部/大类为主，技术主题识别在其下进行。

## 5.4 技术主题抽取

结合专利标题、摘要和技术功效信息，提取具体技术主题。

主要步骤：

1. 对标题、摘要进行文本清洗。
2. 使用中文分词工具（jieba）进行分词处理。
3. 构建新能源汽车技术领域专用词典。
4. 使用 TF-IDF 提取具有代表性的技术关键词。
5. 根据关键词及规则进行技术主题归并，形成"关键词—主题"映射表。
6. 建立专利与技术主题之间的关联。

例如：

| 原始关键词 | 归并后的技术主题 |
|---|---|
| 电池热管理、动力电池热管理 | 动力电池热管理 |
| 电池热失控、热失控预警 | 电池热失控预警 |
| 无线充电、非接触式充电 | 无线充电技术 |
| 电池均衡、单体电池均衡 | 电池均衡技术 |

需要说明的是，技术主题识别采用"自动抽取 + 人工词典归并"的半自动方式，主题边界与归并规则需在说明文档中列明，并通过抽样核对评估效果。IPC 分类主要用于规范技术领域识别，文本抽取主要用于细粒度技术主题识别，两者共同构成技术识别体系。

## 5.5 数据融合

将不同来源的实体和关系进行统一关联：

- 通过公开公告号匹配专利实体。
- 通过标准化申请人匹配创新主体。
- 通过 IPC 分类号匹配技术分类实体。
- 通过统一技术主题名称匹配技术主题实体。
- 通过引用专利公开号建立专利引用关系。
- 通过共同申请专利建立主体间 `CO_APPLIED_WITH` 关系并累计权重。

# 六、知识图谱分析方法

## 6.1 创新主体识别

通过专利申请量、被引证次数及网络中心性等指标识别重要创新主体。

主要指标：

- 专利申请量：反映企业的专利产出规模。
- 被引证次数：反映专利被后续文献引用的情况。
- PageRank：衡量企业在引用关联网络中的结构性影响力。
- 度中心性：衡量企业在合作网络中的直接连接情况。
- 中介中心性：衡量企业在合作网络中连接不同主体的桥梁作用。

不同指标分别展示，不直接合成为缺乏解释依据的综合评分。

## 6.2 企业合作网络分析

根据共同申请专利识别企业之间的合作关系，构建无向加权网络：

- 节点：企业或机构。
- 边：两个企业存在共同申请专利。
- 权重：共同申请专利数量。

通过网络可视化展示合作主体、合作强度及主要合作群体。

## 6.3 技术主题演化分析

根据专利申请日，将技术主题映射到不同年份，统计各技术主题每年的专利数量。

主要指标：

- 年度专利数量。
- 主题年度占比。
- 年度增长率。
- 技术主题排名变化。

通过折线图、热力图及主题排名变化展示技术主题的演化过程。

## 6.4 技术前沿识别

基于技术主题的专利数量和年度增长率，识别具有较高增长趋势的技术方向。

主要指标：

- 技术主题专利总量。
- 最近年度专利数量。
- 年度增长率。
- 技术主题增长趋势。

通过规模—增长率四象限分析识别：

1. 高规模、高增长：重点关注的活跃技术方向。
2. 高规模、低增长：具有一定技术积累的成熟或稳定方向。
3. 低规模、高增长：值得关注的潜在新兴方向。
4. 低规模、低增长：当前专利活动相对较少的方向。

对于低基数导致的异常高增长率，结合专利数量进行判断，避免将少量专利产生的波动误认为重要技术前沿。

## 6.5 技术依赖暴露度分析

基于专利引用关系，衡量企业对外部技术主体的依赖程度。该指标用于回答 CQ10，并在问答页以多跳路径形式展示。

定义：

- 企业 A 的引证总数：`C_A = A 的样本内专利引用其他专利的总次数`。
- A 对主体 B 的引用次数：`c(A,B) = A 的专利引用 B 的专利的次数`。
- A 对 B 的暴露度：`Exposure(A,B) = c(A,B) / C_A`，取值 0—1。

判断规则：

- 当 `C_A` 低于最小样本阈值（如 30 次）时，仅展示数值，不做依赖判断。
- 当某外部主体 B 的 `Exposure(A,B) ≥ 0.5` 且 `C_A` 达到阈值时，标记为"单点依赖"。
- 按技术主题拆分暴露度，识别"在哪个技术方向上更依赖外部主体"。

局限说明：专利引用反映的是技术知识的引用关系，是技术依赖的**代理指标**，不等同于商业采购依赖或供应链依赖。该口径需在说明文档与答辩中明确说明。

### 7.4.4 实体链接

- 企业名：以标准化申请人名称建立候选集，先用别名表精确匹配，再用 rapidfuzz 做近似匹配。
- 技术主题名：以主题名称与关键词表匹配，支持别名。
- 年份：识别"近三年""2020 年以来"等表达，转为年份区间。
- 匹配存在多个候选时，返回候选列表让用户选择，不擅自选择。
- 未匹配到实体时，明确提示"图谱中未找到该主体/主题"，并给出相近候选。

### 7.4.5 查询模板与安全约束

- 每个意图对应一个预置参数化 Cypher 模板，大模型**不生成 Cypher**。
- 所有查询只读（`MATCH`/`RETURN`），禁止写操作。
- 所有查询带 `LIMIT`，并设置查询超时。
- 模板参数经实体链接校验后才拼入查询，避免注入。
- 查询结果统一转为结构化数据（DataFrame / 节点边列表），供展示与结论生成使用。

### 7.4.6 答案生成与可解释面板

结论生成约束：

- 大模型只能使用查询返回的数据，不得引入外部知识或推测。
- 数字必须来自查询结果；数据不足时说明"当前数据不足以判断"。
- 结论控制在 3—5 句，并列出关键数字。

可解释面板展示：

1. 命中的意图与槽位参数。
2. 实体链接结果（含匹配方式与相似度）。
3. 实际执行的 Cypher。
4. 返回的节点、边与原始数据表。
5. 结论与数据的对应关系。

### 7.4.7 技术依赖路径展示

以 CQ10 为例，问答页展示：

```text

  v

  v

  ^
  |
企业B（外部主体）
  |
  v

展示形式：

- 依赖子图（企业 → 主题 → 外部主体）。
- 暴露度排行榜（Top-N 外部主体）。
- "单点依赖"标记与阈值说明。
- 抽样专利明细，支持下钻查看。

### 7.4.8 降级与演示保障

- 大模型 API 不可用时，切换为规则模板答案（基于查询结果拼接），页面标注"规则模式"。
- 提供示例问题按钮，覆盖全部意图，演示时可一键触发。
- 关键演示问题预置查询结果缓存，断网时仍可展示结论、图表与路径。
- 所有查询设置超时，超时返回提示而非页面卡死。

企业A → 专利A → 引用专利B → 企业B → 专利B 所属技术领域
```

业务问题：查询企业A的专利引用了哪些企业的专利，并进一步分析被引用专利所属的技术领域。

对应意图：`Q_CITATION_APPLICANTS`（CQ09）。

## 8.4 多跳示例四：技术依赖与单点依赖

查询路径：

```text
企业A → 专利 → 引用 → 外部专利 → 外部主体 → 技术主题
```

业务问题：某企业的技术引用在多大程度上依赖外部主体，是否存在单点依赖，集中在哪些技术主题。

对应意图：`Q_DEPENDENCY_EXPOSURE`（CQ10）。

# 九、数据质量评价

## 9.1 数据完整性评价

统计关键字段的缺失情况：

- 专利公开号完整率。
- 专利标题完整率。
- 专利申请日完整率。
- 申请人完整率。
- IPC 分类号完整率。
- 专利摘要完整率。

字段完整率公式：

```text
字段完整率 = 非空记录数 / 总记录数
```

## 9.2 实体与关系抽样核对

按作业要求，抽取 50—100 条样本进行人工核对，并报告准确率（P / R / F1）。

抽样方案：

- 分层抽样：按技术领域、年份、申请人规模分层，避免只抽头部企业。
- 核对对象：专利实体、申请人归一化、IPC 关联、技术主题归并、引用方向、共同申请关系。
- 每条样本记录：样本标识、人工判定（正确/错误）、错误类型、核对人。
- 计算各类别的准确率；对实体识别与关系抽取分别统计。

```text
Precision = TP / (TP + FP)

Recall = TP / (TP + FN)

F1 = 2 * Precision * Recall / (Precision + Recall)
```

## 9.3 问答效果评估

构建 20—30 道测试问题，覆盖全部意图，评估：

- 意图识别准确率：问题被路由到正确意图的比例。
- 实体链接准确率：企业/主题/年份被正确解析的比例。
- 答案事实正确率：结论中的数字与查询结果一致的比例（人工判定）。
- 降级可用性：断网/无 API 时，示例问题能否正常返回结果。

测试集同时作为系统回归测试与演示脚本的基础。

## 9.4 评价结果呈现

在说明文档中汇总：

- 字段完整率表。
- 抽样核对混淆矩阵与 P/R/F1。
- 问答测试集结果表。
- 主要错误类型与改进措施。

# 十一、项目特色与创新点

## 11.1 选题创新：从"看图谱"到"问图谱"

多数专利分析停留在统计图表层面。本项目将知识图谱与自然语言问答结合，让不具备 Cypher 能力的业务人员直接提出问题，系统返回可追溯的结论与关联路径。

## 11.2 技术创新：可控的图谱增强问答（KG-RAG 风格）

- 大模型只负责意图识别与语言组织，事实由图谱确定性查询提供，避免幻觉。
- 不采用"大模型自由生成 Cypher"，而以"意图 + 参数化模板"保证安全与稳定。
- 明确区分本方案与微软 GraphRAG（后者包含实体抽取、社区发现与摘要，本项目未采用），并在文档中说明取舍。

## 11.3 功能创新：结论、数据、路径、依据四件套

- 每个回答同时给出结论、数据表、关联路径图与查询依据。
- 可解释面板展示意图、参数、Cypher 与原始数据，回答"这个结论怎么来的"。
- 大模型不可用时自动降级，保证演示连续性。

## 11.4 需求与设计创新：能力问题可执行化

- 将能力问题清单直接编译为"意图—查询模板—页面"的映射表。
- Schema 迭代记录与取舍依据显式化，体现"业务问题驱动建模"的过程。
- 需求、查询、展示三者一一对应，降低沟通与维护成本。

## 11.5 资源创新：用引用网络刻画技术依赖

- 在不具备供应链数据的条件下，利用公开专利的引用关系构造技术依赖暴露度指标。
- 通过多跳路径识别单点依赖，为"技术风险"提供可解释的图谱证据。

## 11.6 管理创新：两天冲刺的范围与风险控制

- 提前冻结范围，明确"做什么、不做什么"。
- 按关键路径并行分工，数据先行、问答在后。
- 预设降级模式与演示脚本，把不确定性转化为可控风险。

# 十四、局限分析与后续扩展

## 14.1 局限分析

1. **数据范围有限**：样本为新能源汽车相关专利的子集，结论不能直接外推到全产业。
2. **引用是代理指标**：专利引用反映技术知识关联，不等同于商业采购或供应链依赖；依赖暴露度仅作参考。
3. **主题识别为半自动**：技术主题依赖关键词与人工词典归并，存在边界模糊与漏识别，已通过抽样核对评估但仍有误差。
4. **实体归一化不完美**：标准化申请人仍可能存在子公司、集团与别名混用，影响合作网络与排名。
5. **问答覆盖有限**：意图库为封闭集合，超出范围的问题只能提示示例，不能自由作答。
6. **未做技术替代推断**：仅凭引用与增长难以证明"替代"，本项目未将其作为结论输出。
7. **规模扩展未验证**：当前方案面向课程规模数据，数据量扩大后需重新评估索引、预计算与查询性能。

## 14.2 后续扩展

- 扩展技术主题体系与领域词典，提升主题识别覆盖率。
- 引入 GraphRAG 的社区发现与摘要能力，支持全局性问题的回答。
- 增加供应链、政策与企业经营数据，将"技术依赖"扩展为"商业与供应链风险"。
- 将意图库升级为可配置的查询编排，支持用户自定义问题模板。
- 增加问答结果的置信度与引用来源标注。

# 十五、项目总结

本项目以新能源汽车产业专利数据为基础，构建专利知识图谱，并在图谱之上实现可解释的智能问答，配合产业全景与创新主体分析页面，形成面向产业技术情报的轻量应用。

项目坚持"做小、做透、说实话"：范围收敛为三个页面，问答采用可控的 KG-RAG 方案，技术依赖以引用网络为代理指标并明确其局限。最终交付一个可运行、可演示、可解释、可评估的知识图谱应用系统。
