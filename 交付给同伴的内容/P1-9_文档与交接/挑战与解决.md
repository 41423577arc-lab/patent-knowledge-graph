# P1 数据与图谱：主要挑战与解决方式

> 适用范围：P1-1 ~ P1-9（数据探查、清洗、技术识别、引用合作、校验、样例、Neo4j、质量与交接）。
> 结论先说：主要挑战集中在六件事——**数据不是随机全量、同一申请多次公开、外部引用不完整、主题规则有误差、企业别名不能硬并、样例与全量必须同构**。有些问题已经彻底解决，有些只能通过口径、边界和辅助表管理。

## 二、逐项说明

### C1 数据不是随机全量

**现象**：原始数据是 16 个 xlsx，合并后 142,112 行 × 204 列。1,008 行抽样显示，14 个批次全部为“授权”，2 个批次全部为“驳回”，说明批次是按法律状态分层导出的，不是随机抽样。2024 年申请 6,519 件、2025 年申请 236 件，明显不完整。

**影响**：如果直接说“106,393 件新能源汽车专利”，老师会追问这是不是全量；如果用 2024—2025 做趋势，会得出错误结论。

**处理**：

- 把数据定位为“课程研究数据集”，不称“全量产业数据”。
- 所有页面和文档标分母：106,393 全量、86,814 技术类。
- 趋势窗口固定用 2010/2015—2023，2024—2025 只展示、不下结论。
- 在 `data_quality.json` 和 `page_metrics.md` 里写清批次分层和不完整年度。

**结果**：规模数字可用，但不会被误读成全量；这是“管理边界”，不是“彻底修复”。

### C2 同一申请多次公开，按申请号去重

**现象**：142,112 行只有 106,393 个唯一申请号，35,719 行是重复或非代表记录；34,006 个申请号对应多行。同一申请会有申请公开、授权公开等多次公开，公开号不同但本质是同一件专利。

**影响**：按公开号统计会重复计数；按行数统计会把 14 万行当成 14 万件专利。

**处理**：

- 以申请号为主键去重，一个申请号保留一条代表公开。
- 代表公开优先级：发明授权 > 发明申请 > 实用新型 > 外观设计；同类型取最早公开。
- 有主文献时删除译文、检索报告、修正/更正、短期专利等非主文献；只有非主文献的申请保留其非主文献（2,090 个）。
- 申请日晚于公开日的 2 条异常，置空申请日/申请年，保留公开日。

**结果**：106,393 件专利；35,719 行被收敛；34/34 结构校验通过，主表 `patent_id` 唯一、子表无悬空编号。

### C3 字段缺失：不伪造，但把缺口讲清楚

**现象**：申请人类型缺失 40.5%，IPC 缺失 14.8%，技术功效缺失 23.2%，被引证专利缺失 61.8%。清洗后仍有 40 件无申请人、868 件非外观设计无 IPC、15,327 件无主题、9,197 件无功效。

**影响**：如果强行填充，会制造假数据；如果不说明，老师会问“为什么覆盖率不是 100%”。

**处理**：

- 缺失一律 `null`，不填 0、不猜日期、不猜分类。
- 外观设计保留在 `patents`，但不写入 IPC、主题、功效三张技术表。
- 申请人类型为空时：境外申请人填“境外/未知”，中国申请人保持空值。
- 覆盖率单独统计，分母用 86,814 件技术类专利，不用 106,393。
- 源表没有的属性（如 `Applicant.country`、`IPC.name`、`Technology.description`）留空，不伪造。

**结果**：IPC 覆盖 99.0%、主题 82.35%、功效 89.41%；缺口写入 `data_quality.json` 和 `contract_check.json` 的警告，页面按“未知”展示。

### C4 引用覆盖低：不建占位节点，改用辅助表

**现象**：引用边 442,917 条，但只有 35,114 条能落到样本内（7.93%）；外部被引 407,803 条，其中有主体明细的只有 15,908 条（3.90%）。kind code 归一后还有 17 组 base 冲突。

**影响**：如果给外部专利建占位节点，图上看起来“引用很全”，实际大部分节点没有标题、申请人、技术分类，会制造假全量；如果不建，引用网络又很稀疏。

**处理**：

- `CITES` 只以样本内专利为引用方，只导入样本内 35,114 条。
- 外部被引不建占位节点；能对齐主体的外部引用写入 `external_citation_applicants` 明细表（46,539 行）。
- 企业级引用另做 `company_citation_pairs.parquet`（135,007 个主体对），标明是“引用集合里出现过”的聚合，不是精确专利边。
- 依赖分析加覆盖率标签；`C_A < 30` 时只展示数值，不做单点依赖判断。

**结果**：图谱里的引用边可追溯、不掺假；依赖分析能用，但必须带“基于 X 件引用专利 / Y 个主体”的说明。这是“用辅助表管理不完整”，不是“把外部引用补全”。

### C5 主题规则误差：把 `（未细分）` 单列，用 100 条量化

**现象**：技术主题靠 40 条关键词规则，宽泛词（电机、热管理、电池、回收、芯片、换电、热失控）会过匹配；16,839 行是 IPC 兜底的 `（未细分）`，占主题行 16.1%。100 条核对中主题准确率 67.5%，非外观设计 60.4%，15 条错误、35 条部分正确。

**影响**：主题排名和年度趋势会被噪声影响；如果把 `（未细分）` 混进细粒度主题排名，会误导。

**处理**：

- 每条专利最多 3 个主题，按关键词命中长度排序。
- 没有关键词命中时，按主 IPC 给一个 `（未细分）` 兜底主题，并单独标记。
- `topic_quality.csv` 把 `（未细分）` 单列，页面排名不混入。
- 100 条分层抽样逐条核对，`notes` 记录原因；错误类型分成“兜底过粗、宽泛词误命中、空主题漏检、部分正确”。
- 没有为了追求指标重跑词典，避免破坏已交付的样例和图谱；把改进建议写进文档。

**结果**：主题覆盖 82.35%；主题准确率 67.5%（非外观设计 60.4%）；错误类型可解释，后续可以按负向规则和词典继续改。

### C6 企业别名：只做展示层，不硬并

**现象**：27,557 个标准化申请人里仍有中英文变体、截断名和集团名，例如 `比亚迪司`、`马自达司`、`Kia Corporation` / `Kia Corp`、`Toshiba` / `东芝公司`。但 `Kia` 与 `Hyundai` 是不同集团，`中国南方` 的原始申请人多数指向重庆长安新能源，不能直接合并。

**影响**：不合并，合作网络和企业排名会碎片化；硬合并，会把不同集团误并，错误更严重。

**处理**：

- 只做展示层别名表 `company_alias.csv`，393 条：人工 116、英文规则 276、待核 1。
- 别名表不修改七张表，也不修改 Neo4j 节点名称；页面读取时再映射。
- `Kia` 与 `Hyundai` 明确不合并；`中国南方` 标 `pending_review`，不硬并。
- 合并后合作边 9,826→9,750（删除 22 条自环），企业主体 27,190 个。

**结果**：展示层可读性提升，同时保留回溯能力；这是“展示层归一”，不是“完整实体消解”。

### C7 样例与全量：同名同列，校验 scope 和 SHA-256

**现象**：P2/P3 需要能快速跑的样例，但统计结论必须用全量；如果样例和全量列名不同，或者页面把样例数字当全量，就会出错。P2 还出现过缺少 `company_metrics`、`topic_year` 的问题。

**影响**：页面开发被阻塞；指标版本混用；答辩数字对不上。

**处理**：

- 样例从全量七表重建：400 件分层 + 50 件一跳引用闭包 + 31 件二跳，共 481 件；同名同列。
- `USE_SAMPLE=true/false` 切换 `data/_sample/` 和 `data/processed/`，不静默回退。
- 预计算指标分两份：样例 `company_metrics` 366 家、`topic_year` 295 行；全量 27,557 家、1,293 行。
- `load_result` 校验 scope、列名、行数、SHA-256；样例和全量不混用。
- 每份指标目录有 `metrics_manifest.json`，记录源表行数和参数。

**结果**：P2/P3 可以先用样例开发，再切全量；指标不会串版本；样例只用于开发，不用于对外规模/趋势结论。

### C8 Neo4j 环境与重建：目录、约束、计数

**现象**：Neo4j Desktop 默认数据目录在 C 盘，空间紧张；旧图谱和新 Schema 可能混用；重复导入会产生重复边；约束名冲突会导致导入失败。

**影响**：C 盘爆满；图数据不可复现；节点/关系数和 parquet 对不上。

**处理**：

- 用环境变量 `NEO4J_DESKTOP_DATA_PATH=D:\Neo4jData` 把数据目录迁到 D 盘。
- `scripts/build_graph.py` 导入前检查目标标签是否已有节点；非空且没有 `--reset` 时直接退出。
- 先建 5 个唯一约束、2 个索引，再导入；导入后逐项核对节点/关系计数，不一致就失败。
- 全量导入约 125 秒，导入后 147,174 节点、571,663 关系。

**结果**：图可以重建、可以核对；CITES 只保留样本内 35,114 条，外部不建占位节点。

### C9 Schema 迭代：版本化，表和图同步

**现象**：最初只有 Patent、Applicant、IPC 和 3 类关系；后来为了主题、合作网络和问答，逐步加入 Technology、Domain、`CO_APPLIED_WITH`、`is_in_sample`、边属性 `is_first`/`is_main`/`weight`。如果下游按旧结构写查询，会返工。

**影响**：P2/P3 的 Cypher 和表读取可能对不上；文档和实际结构不一致。

**处理**：

- Schema 按 V1—V4 记录，每次迭代写清“改了什么、为什么改”。
- 七张表结构和 Neo4j 结构同步；边属性、节点属性写进 `docs/schema.md`。
- 展示层别名、企业级引用、预计算指标放辅助表，不混入核心七张表。
- 34 项结构校验覆盖列名、唯一键、外键、空值、dtype、关系一致性。

**结果**：5 类节点、6 类关系稳定；P2/P3 按统一结构读取；迭代记录保留在 `docs/项目规划.md` 第 4.4 节和 Git 历史。

### C10 100 条人工核对：没有现成标签，就自己定口径

**现象**：100 条抽样没有现成标签；主题判断有主观性；如果只报一个总数，老师无法判断误差来源。

**影响**：无法直接报告准确率；容易只报好数字，或者把结构校验 34/34 当成语义准确率。

**处理**：

- 分层抽 100 条：发明授权 40、实用新型 23、发明申请 19、外观设计 18；覆盖无 IPC、无主题、无功效、有引用、多申请人。
- 每条按 `1`（正确）、`0.5`（部分正确）、`0`（错误）标注，`notes` 写原因。
- 字段级准确率按 `(1×正确 + 0.5×部分) / 已核对条数`。
- 引用按边核对 P/R/F1；合作只统计 9 条多申请人专利，91 条单申请人无共同申请对，不进入分母。
- 明确说明：申请人、IPC、功效、引用、合作都由同一清洗/抽取链路直接生成，100% 只代表“抽样没发现结构化错误”，不代表全量无错，也不能外推为主题准确率。

**结果**：申请人、IPC、功效、引用 100%；主题 67.5%（非外观设计 60.4%）；引用 418 条边 P/R/F1=1.00；合作 9/9。主题错误类型和改进方向写进 `manual_sample_100.md`。

### C11 5 人并行：先给框架，再各自开发

**现象**：5 个人、两天时间，如果按“一个人做功能 A、另一个人做功能 B，再对齐”的方式，容易出现等待和返工。

**影响**：进度被接口对齐拖慢；P2/P3 可能等 P1 的全量数据。

**处理**：

- 按垂直切片分工，一个文件只有一个主人；P1 负责数据与图谱，P2/P3 各自负责页面。
- 先冻结七张表结构、字段名和读取接口；T0 交付样例数据，P2/P3 先用样例开发。
- P1 提供 `load_table` / `load_result` / `run_query` 三个入口；P2/P3 不直接碰底层文件。
- 交接文档写清字段、分母、时间窗口和不能下的结论。

**结果**：P2/P3 不必等全量图；P1 可以独立重建数据；接口变更走文档和版本记录。

## 四、答辩时怎么讲

1. **先讲边界，再讲结果**：先说“这是 16 个批次分层导出的研究数据集，不是随机全量”，再报 106,393 件、86,814 件技术类，避免老师把数字理解错。
2. **讲一个具体链路**：例如“142,112 行 → 35,719 行重复/非代表 → 按申请号去重 → 106,393 件”，比只说“我们做了清洗”更有说服力。
3. **主动说局限**：外部引用只有 7.93%、主题准确率 67.5%、别名不是完整实体消解。主动说边界，比被追问后再解释更可信。
